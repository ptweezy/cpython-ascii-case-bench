# cpython-ascii-case-bench

Benchmarks for [python/cpython#161155](https://github.com/python/cpython/issues/161155), which speeds up ASCII `str.lower()`/`str.upper()` and `bytes.lower()`/`bytes.upper()` by converting a machine word at a time.

The `bench` workflow builds CPython `main` at the patch's parent commit twice on each GitHub-hosted runner: once unchanged, once with `gh-161155.patch`. Since 2026-11-03 that patch is the PR's latest revision (9433a66), which has `varJ`'s code; before that it was `varG2`, and the first version is `variants/varA.patch`. Then it:

- runs `edge_cases.py`, `check_all.py` and `test_str`, `test_bytes`, `test_userstring` and `test_string` on the patched build. `check_all.py` puts every byte value (every ASCII character for `str`) at every position of every length 0..80, and of lengths around word multiples up to 4,096, and checks `lower()`, `upper()`, `capitalize()` and `casefold()` of `bytes`, `bytearray` and `str` against `translate()`, including unaligned `bytearray` buffers;
- compiles `word_exhaustive_word.c` and `variants/gcheck_G.c` with the runner's C compiler and checks the word-level conversion, and the whole functions at lengths 0 to 80, against a per-byte reference;
- on Linux and macOS, disassembles the word helper in the patched binary and counts its SIMD instructions (`vec_check.sh`), to show whether the compiler vectorized it;
- times both builds with pyperf (`bench.py`), alternating between them one benchmark at a time: `str.lower`, `str.upper`, `bytes.lower` and `bytes.upper` at each length, on inputs that cycle through all 128 ASCII characters (`str`) or all 256 byte values (`bytes`) in a fixed shuffled order, plus two lists of short words.

The `check` workflow compiles `exact/check_exact.c` against the PR's word helpers, copied verbatim from `Objects/bytes_methods.c` with the patch applied (`exact/extract.py`), for both word loops (the one MSVC gets and the other). It checks every byte value at every position of a word on all 256 fills and every pair of values at every pair of positions, then the whole functions at many lengths and source and destination offsets, against a per-byte reference. It runs with gcc and clang on Linux (x86-64, arm64) and macOS (arm64, x86-64), MSVC on Windows (x64, x86, arm64), and under QEMU for 32-bit x86 and ARM and big-endian s390x and 32-bit PowerPC.

The matrix covers Linux, Windows and macOS on x86-64 and arm64, each with a plain release build and a PGO build (PGO+LTO on Linux and macOS), two runs each. Linux and macOS also get a `novec` build: release with the compiler's auto-vectorizer turned off for both trees (gcc `-fno-tree-vectorize`, clang `-fno-vectorize -fno-slp-vectorize`). Windows has none because MSVC's auto-vectorizer can't be switched off the same way. Each job uploads its pyperf JSON, a `compare_to` table and the CPU model as an artifact.

```
gh workflow run bench.yml
```

The `variants` workflow compares several versions of the change (the patches in `variants/`) against `main` on each runner. Its `build` input picks release, pgo or novec builds (as in `bench`), or o2 (`CFLAGS=-O2`, which configure puts after its own `-O3`; the Debian-based Docker `python` images (through `EXTRA_CFLAGS`) and Alpine's `python3` (through `CFLAGS_NODIST`) end up at `-O2` the same way, but with PGO, which the `layout` workflow covers with `build=pgo` and `cflags=-O2`), and `bench_set` picks the short-string set or the full one:

- `varA` is the change as proposed.
- `varC` moves the word loop into one helper marked `Py_NO_INLINE`, which the lower and upper functions call only for strings of at least one word.
- `varD` is the same helper as plain `static inline`.
- `varE` is `varA` with an early return through the plain byte loop for strings shorter than a word.
- `varG` keeps the existing byte loops unchanged for short strings. For strings of at least a word, it calls one shared `Py_NO_INLINE` helper (a tail call) that converts whole words, the last one overlapping the one before it. `variants/gcheck_G.c` checks it against a per-byte reference.
- `varF` is `varG` with the helper left `static inline`.
- `varG2` is `varG` with the two small helpers marked `Py_ALWAYS_INLINE`. Without it, gcc's PGO+LTO build treats the word helper as cold (the PGO training doesn't reach it) and calls the per-word function instead of inlining it (1.4x instead of 2.1x at 1,024 characters locally); MSVC's PGO build loses some too (1.9x instead of 2.3x). Normal builds compile to the same code as `varG`.
- `varH` is `varG2` with the word loop counting words (indexing an array-of-words type) and its two constants computed before the loop, so MSVC vectorizes it; the word count is unsigned so size-optimized builds don't use a division.
- `varI` keeps `varG2`'s byte-stepping loop except under MSVC, which gets `varH`'s count-by-one loop; counting words makes clang use post-indexed loads and stores on AArch64, which are slower on Apple cores. Both branches compute the constants before the loop and convert the overlapping last word first.
- `varJ` is `varI` with the overlapping last word converted after the loop again, as in `varG2`, so outside MSVC it is `varG2` with the constants passed in. The PR's latest revision (9433a66) is `varJ` with shorter comments.
- `varK`, `varL` and `varM` are the PR's latest revision (9433a66) with an explicit path for strings shorter than a word, instead of the byte loop. gcc's PGO+LTO build stops peeling that loop once long strings no longer go through it (its training count falls under the link-time hot threshold), which costs about 0.5 ns at length 5. `varK` uses a fall-through `switch` over the lengths 7..1. `varL` converts lengths 4..7 as two overlapping 4-byte words and 2..3 as two overlapping 2-byte words, with a 32-bit `ascii_case_bits32()`. `varM` gives `ascii_case_word()` a byte count, so lengths 4..7 take two overlapping 4-byte words and 1..3 the bytes at 0, len/2 and len - 1, and `_Py_bytes_lower()`/`_Py_bytes_upper()` become one line each.
- `varV` is the PR's latest revision with `__builtin_memcpy` instead of `memcpy` in `ascii_case_word()` under gcc and clang. With `_FORTIFY_SOURCE` (on by default in the macOS SDK, and in many Linux distributions' builds), `memcpy` becomes a checked call that keeps clang from vectorizing the word loop; gcc vectorizes it either way.
- `varX` is `varV` with two words per loop iteration outside MSVC, both loaded before either is stored, and the last pair (or, below 16 characters, the last word) overlapping. At `-O2`, gcc keeps a loop over single words scalar (its cheap cost model won't add a remainder loop or an overlap check), but it vectorizes the pair, so distribution builds get the vector loop too. MSVC's branch is unchanged.
- `varY` is `varV` plus a 16-byte path where `_Py_HAVE_EFFICIENT_BUILTIN_SHUFFLEVECTOR` is defined (gcc or clang on x86-64, ARM64, or ARM32 with NEON; the check that `Python/pystrhex.c` uses for `bytes.hex()`): strings of 16+ characters go through a loop over a GNU vector of words (`vector_size(16)`), with the same bit trick and the last 16 bytes overlapping. It compiles to SSE2 or NEON without the auto-vectorizer, so it stays vectorized at `-O2` and in PGO builds that find the loop cold. Shorter strings and MSVC are unchanged.
- `varP` is the PR's latest revision with strings of 16+ characters converted in 16-byte blocks outside MSVC: each block is an array of words (`size_t x[16 / SIZEOF_SIZE_T]`, memcpy in, `ascii_case_bits()` on each, memcpy out), the last block overlapping. Plain C11, no compiler extensions: gcc and clang turn each block into one SSE2 or NEON operation at -O2 and with `_FORTIFY_SOURCE` (so it needs no `__builtin_memcpy`), and in gcc 13-15 and clang PGO builds where the loop is cold; gcc 16 PGO leaves it scalar on x86-64. Suggested by an adversarial review of `varY`.
- `varQ` is `varP` plus `varW`'s overlapping words for strings shorter than a word.
- `varR` is `varP` with the same 16-byte block loop for every compiler, and the PR's MSVC-only count-by-one loop removed: below 16 bytes only one or two words remain, so that loop no longer matters. On x64, MSVC turns the array block into SSE2 code at /O2 and also at /O1 /Oi (as for code that PGO finds cold), where the PR's loop is scalar; on 32-bit x86 it leaves the block scalar at /O1 /Oi and in PGO builds, and at /O2 vectorizes it only behind a run-time CPU check. On gcc and clang it compiles to the same code as `varP`.
- `varS` is `varR` plus `varW`'s overlapping words for strings shorter than a word.
- `varT` is `varR` with the 16-byte block written as a GNU vector (`uint64_t` x 2, `vector_size(16)`) under gcc and clang on x86-64 and ARM64, with every constant splatted explicitly (no scalar operands, so older clang accepts it; see gh-148474). It stays SIMD where gcc and clang optimize for size: gcc 16 PGO builds (Fedora) leave `varR`'s plain-C block scalar. MSVC and other targets keep `varR`'s plain-C block.
- `varU` is `varT` plus `varW`'s overlapping words for strings shorter than a word.
- `varN` is `varT` with a 32-byte vector block (`uint64_t` x 4) where `__AVX2__` is defined (`-march=x86-64-v3` and up), so strings of 32+ characters go 32 bytes at a time and 16 to 31 through the word loop. With AVX2, gcc and clang `-O3` turn the PR's word loop into a 32-byte AVX2 loop but keep `varT`'s 16-byte vectors at 16 bytes, so there `varT` is about 0.6x the PR on long strings. Without AVX2, `varN` compiles to the same machine code as `varT`.
- `varO` is `varN` with the 32-byte vector block for every gcc/clang build on 64-bit x86 and arm64, not only with AVX2. On arm64 it matches clang's unrolled loop for the PR; on x86-64 without AVX2 gcc lowers the 32-byte vector badly (in PGO builds slower than `main`).
- `varB` is the recommendation in [`VARIANTS.md`](VARIANTS.md): the GNU vector block for gcc and clang on 64-bit x86 and arm64 (32 bytes on arm64 and with AVX2, 16 bytes with SSE2), the two-word array block only for 64-bit MSVC, and the PR's word loop, unchanged, everywhere else (32-bit targets, where MSVC leaves the four-word array block scalar in PGO builds and slower than the word loop otherwise; clang-cl; other targets). It compiles to `varT`'s code on x86-64 without AVX2, `varN`'s with AVX2, `varO`'s on arm64, and the PR's on 32-bit Windows.
- `varB5` is `varB` plus a 64-byte vector block where `__AVX512F__` is defined (`-march=x86-64-v4`). Elsewhere it compiles to `varB`'s code. In uv's x86-64-v4 configuration (measured with clang 21 PGO+LTO; uv's own builds use clang 23) it measured 0.39-0.78x `varB` at 64K on Intel Xeons, so it isn't offered.
- The `cmp*` variants are compact versions, against the issue's estimate of about 35 lines:
  - `cmpA` (50 non-blank lines, one `#ifdef _MSC_VER`, plain C): on 64-bit targets, 16-byte blocks of two words first, then the word loop counting by one for every compiler. The block is a two-iteration loop under MSVC (which vectorizes that loop but not straight-line code) and two straight-line statements elsewhere (which gcc 16 keeps vectorized in PGO-cold code, unlike the loop).
  - `cmpB` (46 lines, no `#if`) is `cmpA` with the loop form of the block for every compiler.
  - `cmpC` (56 lines) is `cmpA` with the block as two separate words (two loads into two variables) outside MSVC: in Fedora's gcc 16 PGO build `cmpA`'s two statements on an array stayed scalar, while `varX`'s separate words were vectorized.
  - `cmpD` (56 lines, one `#if`) is `cmpC` with the `#if` choosing gcc (`__GNUC__` and not `__clang__`) instead of MSVC: gcc gets the separate words, clang and MSVC the two-word array loop. It compiles to `cmpB`'s code under clang and `cmpC`'s under gcc (`tests/same_code.sh`).
  - `cmpM` (35 lines, no `#if`) is the PR's design made smaller: one count-by-one word loop for every compiler.
  - `cmpMi` (44 lines) is `cmpM` with the PR's MSVC-only loop kept; it compiles to the PR's loops.
  - `cmpT` (88 lines) is `varB` in fewer lines, with the same machine code on every target checked (`tests/same_code.sh`).
- `varW` is `varL` (overlapping words for strings shorter than a word) plus `varV`'s `__builtin_memcpy`. On shuffled real-world length mixes (`realworld/`), `varL` was the fastest short path on an Apple M4 and on x86 with gcc and clang, release and PGO.

```
gh workflow run variants.yml
```

The `layout` workflow compares variants with code placement averaged out, since moving identical code by a few bytes changes its speed by more than the variants differ. Each tree is linked once per shift with a padding object of 0 to 4,080 bytes linked ahead of Python's object files (in gcc PGO builds the hot and cold sections still come first, so the padding moves ordinary code such as `ascii_case_words` but not the interpreter loop). Then the real-world short-string replay (`realworld/replay_drive.py`), fixed lengths (`realworld/len_layout.py`) and string operations that never reach the case code (`realworld/control.py`, a check on whole-build differences between PGO builds) run over every build and shift. It records the SIMD instruction count of each tree's `ascii_case_words` (`results/simd.txt`). Its inputs pick the build (release, o2, lto, which is LTO without PGO as FreeBSD's ports build, or pgo), the compiler (`cc`), extra `cflags`, the PGO training task (`profile_task`), a Fedora image to build in (`container`, for the gcc that Fedora ships) and whether to upload the binaries. [`VARIANTS.md`](VARIANTS.md) sums up the results.

```
gh workflow run layout.yml -f variants="varJ varR varT varN" -f build=pgo
```

The `oldcc` workflow checks the variants' word and block helpers with old compilers: every gcc and clang that Ubuntu 16.04, 18.04 and 20.04 package, on x86-64 and arm64. It copies the helpers verbatim from `Objects/bytes_methods.c` with each patch applied (`oldcc/make_test.py`), builds them at `-O0` to `-O3` and `-Os` (and with AVX2 on x86-64), checks every byte value at every position of every length from 8 to 100 bytes in both cases, and counts the SIMD instructions in `ascii_case_words` (`oldcc/run_all.sh`).

```
gh workflow run oldcc.yml -f variants="varJ varR varT varN"
```

`tests/` holds the tests proposed for the PR (`proposed_tests.py`, runnable against any build; `add_tests.py` and `tests.patch` put them where a PR would), the mutation check that shows what they catch (`mutation_check.sh`, `mutants.py`), and `same_code.sh`, which compares the machine code of two variants' helpers across compilers and targets.
